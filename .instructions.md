# Coding Instructions

## Core Principles

### Test-Driven Development (TDD)

**Always implement features using the TDD red-green-refactor cycle:**

1. **Write a failing test first** - Create tests that define the expected behavior before writing implementation code
2. **Implement minimal code to pass** - Write only enough code to make the test pass
3. **Refactor with confidence** - Use passing tests as safety net to improve code structure

**Test Requirements:**

- Tests must cover all public APIs and business logic
- Include edge cases, error conditions, and boundary values
- Tests should be independent and deterministic
- Aim for high coverage on core functionality

### Code Readability & Maintainability

**All code must prioritize clarity over cleverness:**

#### Naming Conventions (Python)

- Use descriptive, self-explanatory names
- Avoid abbreviations unless universally understood
- Function names should describe the action, not just the data transformation
- Variable names should be clear about their purpose and type

```python
# Good: Clear intent
def calculate_user_subscription_revenue(user_id):
    return get_user_subscriptions(user_id).total_amount

# Bad: Unclear intent
def calc(u):
    return s.t()
```

#### Naming Conventions (JavaScript/Node.js)

- Use descriptive, self-explanatory names
- Avoid abbreviations unless universally understood
- Function/method names should describe the action, not just the data transformation
- Variable names should be clear about their purpose and type

```javascript
// Good: Clear intent
function calculateUserSubscriptionRevenue(userId) {
  return getUserSubscriptions(userId).totalAmount;
}

// Bad: Unclear intent
function calc(u) {
  return s.t();
}
```

#### Code Structure (Python)

- Keep functions small and focused (single responsibility)
- Extract complex logic into helper functions with clear names
- Use meaningful comments only for non-obvious business rules
- Avoid magic numbers; use named constants

#### Code Structure (JavaScript/Node.js)

- Keep functions/methods small and focused (single responsibility)
- Extract complex logic into helper functions with clear names
- Use meaningful comments only for non-obvious business rules
- Avoid magic numbers; use named constants

#### Error Handling

- Handle errors explicitly where behavior differs based on error type
- Log errors appropriately without exposing internal details
- Fail fast with clear error messages during development

## Implementation Guidelines

### When Adding New Features

1. Write tests for the new functionality
2. Implement the feature minimally to pass tests
3. Review code for clarity improvements
4. Add documentation comments for complex logic

### When Modifying Existing Code

1. Ensure existing tests still pass (regression testing)
2. Update or add tests if behavior changes
3. Keep modifications minimal and focused
4. Document any architectural decisions in code comments

## File Organization

- Group related functionality together
- Use clear, descriptive file names
- Keep imports organized and sorted
- Separate configuration from implementation logic

## Documentation Standards

### Code Comments

- Explain **why** something is done, not **what** (code should be self-documenting)
- Document non-obvious business rules or algorithms
- Add docstrings to public functions with clear parameter/return descriptions

### Function Documentation Template

```python
def function_name(parameters):
    """
    Brief description of what the function does.

    Args:
        param1 (type): Description of parameter 1
        param2 (type): Description of parameter 2

    Returns:
        type: Description of return value

    Raises:
        ExceptionType: When and why this exception is raised
    """
```

## Testing Standards

### Test File Organization

- Tests should be in separate files or clearly separated sections
- Group tests by feature/module
- Use descriptive test names that explain the scenario being tested

### Test Naming Convention

```python
def test_<feature>_<scenario>_returns_<expected_result>():
    # ... test implementation
```

Examples:

- `test_user_login_with_valid_credentials_returns_success()`
- `test_payment_processing_with_insufficient_funds_raises_error()`
- `test_data_export_handles_empty_dataset_gracefully()`

## Code Review Checklist

Before committing code, verify:

- [ ] All tests pass (including new and existing)
- [ ] New functionality has corresponding tests
- [ ] Code follows readability principles
- [ ] No unnecessary complexity introduced
- [ ] Error handling is appropriate
- [ ] Documentation comments added where needed
- [ ] Variable/function names are descriptive

## Anti-Patterns to Avoid

❌ **Don't write code first, then test** - This defeats the purpose of TDD  
❌ **Don't use overly clever one-liners** for complex logic  
❌ **Don't nest loops deeper than 3 levels** without extraction  
❌ **Don't leave TODO comments** without addressing them promptly  
❌ **Don't duplicate code** across multiple locations

✅ **Do write tests that fail before implementation**  
✅ **Do use clear, explicit variable names**  
✅ **Do extract complex logic into well-named helper functions**  
✅ **Do address technical debt immediately when noticed**  
✅ **Do prefer composition over inheritance for flexibility**
